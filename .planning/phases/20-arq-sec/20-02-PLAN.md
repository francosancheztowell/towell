<objective>
SEC-04: que un error no controlado en una request JSON (window.http, axios, fetch con Accept JSON) no filtre detalle interno en producción y devuelva un código que Sistemas pueda buscar en `/admin` (SYSMonErrorEvento), igual que la página 500.
</objective>

<execution_context>
- Orden del handler de Laravel 12: `report()` (aquí corre `ErrorRecorder::capturar()`, que deja el Id del evento en el singleton scoped `EstadoRequest`) → `render()` → `prepareException()` → callbacks de render. Así que en el callback ya se conoce el evento.
- Hoy, con `APP_DEBUG=false`, Laravel responde `{"message":"Server Error"}` para excepciones comunes, pero **para `HttpException` 5xx devuelve `getMessage()`** (`abort(500, $e->getMessage())`, `abort(503, ...)`). Eso es lo que se filtra, además de no haber trace_id.
- ValidationException (422), AuthenticationException (401), HttpResponseException y las HttpException < 500 (403, 404, 419) no entran al callback: se devuelve `null` y sigue el flujo normal.
- Excepciones con `render()` propio o `Responsable` no pasan por callbacks (Laravel); no cambian.
- Sin SQL nuevo.
</execution_context>

## Diseño

1. **`HandlesApiErrors`**
   - `protected function traceIdDeError(): string` — `EstadoRequest::eventoId` si existe; si no, `Str::uuid()`.
   - `protected function serverErrorResponse(Throwable $e, int $status = 500): JsonResponse` — **no** vuelve a reportar (el handler ya lo hizo); si no hubo evento escribe un `Log::error` con el uuid, la clase y el mensaje (el log es del servidor); responde `{success:false, message: MENSAJE_SERVIDOR, trace_id}`.
   - `apiErrorResponse()` conserva firma y respuesta, pero su `trace_id` pasa a ser el Id del evento que acaba de registrar su propio `report($e)` (D2). El `Log::error` sigue igual.
   - Constante `MENSAJE_SERVIDOR = 'Ocurrió un error en el servidor. Si continúa, comparte el código de referencia con Sistemas.'`
2. **`bootstrap/app.php`** — un `render(function (Throwable $e, Request $request))`:
   - `null` si `config('app.debug')`, si la request no espera JSON (`expectsJson()`), o si es `HttpResponseException` / `AuthenticationException` / `ValidationException`.
   - status = `HttpExceptionInterface::getStatusCode()` o 500; `null` si < 500.
   - Si no: `serverErrorResponse($e, $status)` vía una clase anónima que usa el trait (los traits no se llaman estáticamente en PHP 8.4), conservando los headers de la HttpException (p. ej. `Retry-After` en 503).
3. **Livewire (D1):** las requests de Livewire (`X-Livewire`) **no** mandan `Accept: application/json`; hoy reciben la página 500 HTML (sin detalle con APP_DEBUG=false y con el código de referencia), que Livewire pinta en su modal. Si se les responde JSON, el modal mostraría el JSON crudo y arreglarlo requiere un hook en `resources/js/**` (prohibido aquí). Recomendado: dejarlas en HTML y cubrirlas con un test que pruebe que no filtran detalle. Alternativa: JSON + HANDOFF a FE para un `Livewire.hook('request', fail → notify.error(message + trace_id))`.

## Decisiones para el owner

- **D1 — Livewire.** (A, recomendada) HTML 500 como hoy (sin detalle, con código de referencia) + test. (B) JSON como `window.http` + HANDOFF a FE.
- **D2 — `apiErrorResponse()` usa el Id del evento como trace_id** en vez de un uuid suelto. Recomendado: sí (mismo código que la página 500 y que `/admin`; el uuid sigue como respaldo). El valor pasa de uuid a número en texto; ningún JS lee `trace_id` hoy (grep en `resources/js`).
